# Microsite

The marketing site for the extension, at **https://whatsapp-chats-downloader.otro.digital**.

A single static HTML file with inlined CSS, no build step and no JavaScript. One webfont
(Newsreader, preconnected) and one image; everything else is system fonts and inline SVG, so the
page is fast without a toolchain.

## Files

| File | Purpose |
| --- | --- |
| `index.html` | The whole site: markup, styles and JSON-LD structured data. |
| `og-image.png` | 1200x630 social card, generated by `../tools/make-store-assets.sh`. |
| `browser.png` | Product shot: the real popup UI composed into a browser frame. Same generator. |
| `favicon.svg` | Scalable favicon; `apple-touch-icon.png` is the extension's 128px icon. |
| `robots.txt` | Allows everything, points at the sitemap. |
| `sitemap.xml` | Single URL. Update `lastmod` when the content changes. |
| `CNAME` | Custom domain for GitHub Pages. |
| `.nojekyll` | Serves the files verbatim, with no Jekyll processing. |
| `src/og.html` | Source for the social card. Re-render after editing. Not published. |
| `src/browser-shot.html` | Source for the product shot; pulls the live markup out of `popup.html`. Not published. |

## Deploy

Deployment is automatic: [`.github/workflows/deploy-site.yml`](../.github/workflows/deploy-site.yml)
publishes this folder to GitHub Pages on every push to `main` that touches `site/`. There are no
secrets to configure — Pages authenticates with the repository's own token.

Two one-time setup steps:

1. **Repository → Settings → Pages → Build and deployment → Source: GitHub Actions.**
   Without this the workflow fails at the `configure-pages` step.
2. **DNS.** In the `otro.digital` zone, add a `CNAME` record for
   `whatsapp-chats-downloader` pointing at `otrodigital.github.io`. Then set the same domain under
   Settings → Pages → Custom domain and tick **Enforce HTTPS** once the certificate is issued
   (usually a few minutes).

The `CNAME` file in this folder carries the domain into each deploy, so it survives republishing.

`README.md` and `src/` are excluded from what gets published; everything else in this folder is
served at the domain root.

### Note on headers

GitHub Pages does not support custom response headers, so there is no cache-control or
security-header configuration. Pages sets sensible caching itself and enforces HTTPS/HSTS on custom
domains once **Enforce HTTPS** is on. If you later need header control — a CSP, for instance — that
is the point to move to a host that allows it.

## After the first deploy

1. Confirm the live URL matches the canonical tag exactly — `https://whatsapp-chats-downloader.otro.digital/`,
   https, no `www`, trailing slash. A mismatch splits ranking signals.
2. Add the property in [Google Search Console](https://search.google.com/search-console) and submit
   `sitemap.xml`.
3. Check the structured data with the [Rich Results Test](https://search.google.com/test/rich-results) —
   the FAQ block is eligible for rich results.
4. Preview the social card by pasting the URL into any chat app or LinkedIn's Post Inspector.
5. Run Lighthouse. The page should score near 100 on performance; if it doesn't, the webfont is the
   first thing to look at.

## Editing

Structured data has to keep matching what's on the page — Google penalises FAQ schema that doesn't
appear in the visible content. If you add, remove or reword a question in the `.faq` section, make
the same change in the `FAQPage` block at the bottom of `index.html`.

`node ../tools/check-site.js` re-runs the checks: JSON-LD parses, FAQ schema matches the visible
questions, one `h1`, anchors resolve, meta lengths are within limits.
